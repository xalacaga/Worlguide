# Feature Spec: POI content via extraction (on-device)

**Status**: approved
**Created**: 2026-08-14
**Domain module(s) touched**: iOS: WGConfiguration, WGAdapters (new adapters
+ the first real `ContentProviding`, no new module)

## Overview

[ROADMAP.md Phase 3](../../ROADMAP.md) — the first real implementation of
`WGContent.ContentProviding` (existing Protocol port, only a test fake
behind it so far). [ADR 0010](../../docs/adr/0010-content-via-extraction-not-llm-generation.md)
is the decision that governs this spec's shape: content is **assembled by
extracting real text from sources**, never generated by an LLM. This
reprises the old, deleted `specs/006`, on-device instead of server-side,
built on top of `specs/007` (finding the POI) and `specs/008` (resolving
its Wikipedia title and OSM tags).

## User scenarios

- As a user who has selected a POI, I want the app to show/read me a short
  text about it — a real Wikipedia extract plus, when available, a line
  built from OpenStreetMap facts (period, architect, type) — so that I get
  grounded, sourced content instead of nothing or a hallucination.

## Requirements

- [ ] `WikipediaSummaryExtractor` (new, `WGAdapters`) fetches the Wikipedia
  REST `page/summary/{title}` extract text for a given article title and
  language — reuses `HTTPTransport`. Returns `nil` (not a thrown error) on
  HTTP 404 (article title resolved by `specs/008` but the summary endpoint
  has nothing, e.g. a redirect target that itself doesn't exist) — same
  "expected absence" pattern as `specs/008`.
- [ ] `OSMContentLineComposer` (new, `WGAdapters`, pure — no I/O) composes
  a short line from a POI's OSM tags when the relevant keys are present:
  `tourism`, `historic`, `start_date`, `architect` — same four keys
  [ADR 0010](../../docs/adr/0010-content-via-extraction-not-llm-generation.md)
  specified for the (deleted) backend's `OSMContentExtractor`. Returns
  `nil` when none of the four keys are present.
- [ ] `WikidataCoordinateResolver` (new, `WGAdapters`) resolves a QID to
  its `Coordinate` (`wdt:P625`) via the existing Wikidata SPARQL endpoint
  (`specs/007`'s `.wikidataSparqlEndpoint`, no new config key) — needed
  because `ContentProviding.content(forPOI:language:)` only receives a
  `poiID`, not a coordinate, and OSM tag lookup (`specs/008`'s
  `OverpassTagFetcher`) needs one. Returns `nil` when the QID has no
  coordinate.
- [ ] `WikipediaContentProvider: ContentProviding` (new, `WGAdapters`) —
  the real adapter. Orchestrates, per [ADR 0010](../../docs/adr/0010-content-via-extraction-not-llm-generation.md):
  resolve sitelink title (`specs/008`'s `WikipediaSitelinkResolver`) →
  extract Wikipedia summary → resolve coordinate → fetch OSM tags
  (`specs/008`'s `OverpassTagFetcher`) → compose OSM line → concatenate
  the non-`nil` fragments into `ContentPackage.text`. Reuses `specs/008`'s
  `POISources.assemble` to build `provenance` from the same
  title/tags inputs, instead of duplicating that logic.
- [ ] Validation: if the concatenated text is empty (no Wikipedia extract,
  no OSM line), `content(forPOI:language:)` returns `nil` — "no content
  found," not an error. This is the on-device equivalent of the backend's
  `ContentDraftValidator` (`ADR 0010`/`ADR 0004`).
- [ ] Network/decoding failures at any step surface as `WGError.network` /
  `WGError.decoding` — only "source/coordinate/summary absent" is a soft
  `nil`, not every failure.

## Out of scope

- Smoothing the concatenated Wikipedia+OSM text into one coherent voice
  with an LLM — explicitly deferred by
  [ADR 0010](../../docs/adr/0010-content-via-extraction-not-llm-generation.md)
  ("a new, explicit decision," not this spec).
- Caching `ContentPackage` across app launches or sessions.
- TTS / reading the content aloud (Phase 4/5).
- Wiring into an actual app UI (Phase 5, no Xcode App target yet).
- Choosing which language to request (caller-supplied, unchanged from the
  existing `ContentProviding` signature).

## Provenance / data impact

`WikipediaContentProvider` produces the first real (non-fake)
`ContentPackage.provenance` — reusing `specs/008`'s `POISources.assemble`
means the provenance rule ("a source contributes only if present") is
defined once, not twice. Wikidata itself (via `WikidataCoordinateResolver`)
does not add its own `Provenance` entry — it's an internal lookup this
adapter needs, not source material that ends up in `ContentPackage.text`,
consistent with `specs/007`'s POI `id`/QID already being the Wikidata
provenance link.
