# ADR 0004: Knowledge Package carries explicit provenance end-to-end

**Status**: Accepted
**Date**: 2026-08-13

## Context

WorldGuide's pitch depends on trustworthy content: text generated by an LLM,
about a real place, must be traceable back to what it was grounded in.
Without a provenance model designed in from the start, it is very easy to
end up with generated content that cannot be audited or corrected at the
source.

## Decision

`domain/knowledge/models.py` defines `KnowledgePackage` as carrying, at
minimum:

- one or more `SourceReference` (from `domain/sources/models.py`): which
  source record(s) it was built from, each itself carrying where it came
  from (Wikipedia, Wikidata, or a later institutional source) and when it
  was retrieved.
- `license`: the license/terms under which the source material may be used.
- `validation_status`: set by `domain/validation/`, never by `content/` or
  `llm/` directly — a `KnowledgePackage` cannot be marked valid by the same
  stage that produced it.
- `generation_lineage`: once `domain/content/` produces text from this
  package via `domain/llm/`, the resulting `ContentDraft` records which
  `KnowledgePackage` (by id) and which LLM call it came from.

This is scaffolded now as typed fields with no population logic (no real
ingestion/validation/generation exists yet) so that every future adapter
writes into a provenance shape that already exists, instead of provenance
being bolted on after content generation is already working.

## Consequences

- `domain/content/` cannot express "generated text" without a
  `KnowledgePackage` reference — the type system prevents provenance-less
  content by construction once real logic is added.
- Any future institutional-source integration extends `SourceReference`,
  not `KnowledgePackage` — the provenance chain shape is stable even as the
  number of source kinds grows.
- Storing full lineage has a cost (more fields to populate correctly); this
  is accepted as central to the product's trust model.
